== What is Unix?
image::unix-license-plate.jpg[width=500,,  align="center"]
[.small]#Source: Wikipedia (https://en.wikipedia.org/wiki/Live_Free_or_Die)#

[.step]
* a family of operating systems with similar architecture and similar features
* most important family members today: Linux and macOS
* as well as specifications for operating systems (Single UNIX Specification and POSIX)
* and a culture of its own :-)
* Many IT technologies have their origins in Unix or were popularized by Unix: TCP/IP, C/C++, regular expressions, pipes, and hierarchical file systems.

image::thompson-ritchie.jpg[width=500,,  align="center"]
[.small]#Source: Wikipedia (https://en.wikipedia.org/wiki/Unix)#

[.step]

== A (Brief) History of Unix (2)
[.step]
* 1980s: Emergence of many commercial Unix variants (e.g. SunOS/Solaris from Sun Microsystems, HP-UX from HP, AIX from IBM, SINIX from Siemens, Xenix from Microsoft, NeXTSTEP from NeXT) and the commercial spread of Unix
* 1991: Linus Torvalds releases the first version of Linux.
* 1990s: The spread of Linux and the emergence of various Linux distributions (Red Hat, SUSE, Debian...)
* 2001: Apple releases the first version of macOS (based on NeXTSTEP and FreeBSD).
* 2007: Apple releases the first version of iOS.
* Since the 2000s: Consolidation of commercial Unix variants / Replacement by Linux

== File System
[.step]
* File system = component in the kernel + data structures on the storage medium
* All files and directories are organized in a tree that begins with `/` (the root directory).
* They are uniquely identified by the _path_ = list of all parent directories + their own name; the separator is the forward slash `/`.
* _Absolute_ path: starts with the root directory (`/`), _relative_ path: relative to the current directory
* Multiple file systems (on different storage devices) can be located in different places as subdirectories in the tree (_mounted_).
* In addition to regular files, there are also special pseudo-files: links, pipes, devices, and sockets
* All files and directories are assigned to a user and a group and have access permissions (which do not apply to the root user).
* Standard for the tree structure: https://en.wikipedia.org/wiki/Filesystem_Hierarchy_Standard[_Filesystem Hierarchy Standard_]

== User
[.step]
* To work with a Linux system, you need a user account (which is usually created during installation).
* In addition, there are also system users for various purposes, such as daemons.
* Users are identified by their unique name and, internally within the system, by a (usually) unique number => _User Identifier_ (UID)
* Each user has its own home directory (_Home Directory_), usually located under `/home` (or `/Users` on macOS)
* are managed either in the `/etc/passwd` and `/etc/shadow` files or in a directory service such as LDAP
* are members of at least one group => primary group
* can be members of additional groups (the limit is usually 65536) (configured in `/etc/group` or in a directory service)
* Special user: _root_ with UID 0, the administrator, (usually) has full access to the system


<<<
== Groups
[.step]
* are identified by their unique name and, internally within the system, by a (usually) unique number => _Group Identifier_ (GID)
* are managed either in the `/etc/group` file or in a directory service such as LDAP
* Local groups (managed in `/etc/group`) can only contain users, *not* other groups.

== What is a shell?
[.step]
* is the command-line interface (CLI) of Linux for entering commands and running programs
* is launched when you log in to the console of a Linux system, open a terminal program in a desktop environment, or log in to a system over the network
* It also has built-in commands, control structures, and variables, and is a full-fledged programming language (see _Writing (Simple) Shell Scripts_)
* Several alternatives: sh, ksh, (t)csh, **Bash**, **Zsh**

[.step]
* in some cases more efficient than a graphical user interface
* Small tools can be combined to solve larger tasks => filters and pipelines
* Tasks can be automated using scripts.
* Documenting tasks is easier than with a graphical user interface.
* Working on remote computers connected via the network is easier.

== Structure of a Command Line (1)
image::command-syntax.en.svg[width=1200,,  align="center"]
[.step]
* The shell prompt asks you to enter a command.
* A command line consists of one (or more => pipelines) command(s), options, and arguments.
* Common syntax for describing commands:
[.step]
** Required arguments in angle brackets: `<file>`
** Options or optional arguments in square brackets: `[-x]`
** Alternatives separated by vertical bars: `file|directory`
* Options begin with `-` (short form, one letter) or with `--` (long form, one word or multiple words connected by a dash), as per convention for commands and programs.


<<<
== Structure of a Command Line (2)
[.step]
* How are commands found? There are three ways:
[.step]
** The command is built into the shell (e.g. `cd`).
** The command / program / script is specified with a path.
** The command / program / script is specified without a path and is searched for in the _search path_ = list of directories containing programs / commands / scripts (environment variable `PATH`).
* Shell runs non-built-in commands, programs, and scripts as separate processes.
* Commands, programs, and scripts set the _exit status_ (success/failure) when they terminate => special variable `$?`; 0 indicates success, > 0 indicates failure (the exact values depend on the command, program, or script).
* Running commands, programs, and scripts can be terminated by pressing Ctrl+C.
* Exit Shell: Ctrl-d (or `exit`)


<<<
== Shell History
[.step]
* Shell "remembers" executed command lines (optionally also permanently in a file) => _shell history_
* Scroll through the history: Up/down arrow keys
* Search History: Ctrl-r
* Complete a command from the history (Zsh only): Type the beginning + up arrow key

== Editing the Command Line
[text-left]
Command lines that have been entered or retrieved from the history can be edited. The default keyboard shortcuts for Bash and Zsh are listed here, but they can be changed.

[cols="3,1"]
|===
| Jump to the beginning / end of the line | Ctrl-a / Ctrl-e
| Delete a single character forward / backward | Ctrl-d / Backspace
| Delete a word forward / backward (in Bash, up to the next space; in Zsh, you can configure which characters are considered part of a word (variable `WORDCHARS`)) | Esc-d / Ctrl-w
| Delete line to the beginning / end | Ctrl-u / Ctrl-k
| Reinsert deleted line / word | Ctrl-y

== Additional Features (1)
[.step]
* Commands can read from a file (using `<`) and write their output to a file (using `>`) or append it to an existing file (using `>>`).
* Commands can be chained together using `|` to form _pipelines_ => The output of the first command is the input for the second command.
* Commands can be run in the background by adding `&` at the end of the command line.
* Ctrl-z pauses a running program; `bg` sends it to the background; `fg` brings it back to the foreground.
* Shell can autocomplete commands by pressing the Tab key (files/directories, program names, options, variables).
* Command lines can be saved as aliases (using the `alias` command) or as functions; see the chapter _Writing (Simple) Shell Scripts_.


<<<
== Additional Features (2)
[.step]
* Replace a command with its output (_Command Substitution_): `$()`
+
[source, sh]
----
echo "Hello $(whoami)@$(hostname)"
----
* Use a command as a "file" for input or output (_Process Substitution_, if you can't use a pipeline): `<()` and `>()`
+
[source, sh]
----
diff <(grep "bla" file1) <(grep "blub" file2)
----

== Wildcards (1)
[.step]
* In the shell, you can work with incomplete file and directory names => search patterns or _wildcards_ (also known as _globbing_)
* are evaluated by the shell, not by the commands
* Example: `*.txt` => all files ending in `.txt`
* icon:exclamation-circle[] Note the maximum length (2 MB) of a command line!


<<<
== Wildcards (2)
|===
| Syntax | Meaning

| `?` | any single character
| `*` | any number of characters
| `[xyz]` | one of several possible characters, e.g. the letters x, y, or z
| `[a-e]` | a range of characters, e.g. the letters a through e
| `+[[:alpha:]]+`, `+[[:digit:]]+` | character classes, e.g. letters or digits
| `+*.{jpg,png}+` | Alternatives, e.g. all files ending in either `.jpg` or `.png`
| `+!(*.txt)+` (Bash with the `extglob` option) or `^*.txt` (Zsh with the `extendedglob` option) | Negation, e.g. all files that do not end in `.txt`
|===

== Quoting / Escaping
[.step]
* Most special characters have a specific meaning in the shell (https://tldp.org/LDP/abs/html/special-chars.html[here] is the complete list for Bash).
* Two options if you want to use them "normally":
[.step]
** Enclose them in (single or double) quotes (_quoting_)
** Prefix them with a backslash (_escaping_)
* Difference between single and double quotes:
[.step]
** Single: All special characters (including backslashes) lose their special meaning.
** Double: Some special characters retain their special meanings, particularly `$` (variable expansion) and `\` (escaping); see https://www.gnu.org/software/bash/manual/html_node/Double-Quotes.html[here] for details.

== Environment Variables
[.step]
* Key-value pairs, or a special type of shell variable (see also the chapter _Writing (Simple) Shell Scripts_)
* are used to configure the shell itself and the commands, programs, and scripts being executed (they are passed on to the processes started by the shell)
* Set a variable (in `.bash_profile` / `.zprofile` if you want it to be set permanently; see the next slide): `export <VARIABLE>=<Value>`. The name is usually capitalized, and the value must be enclosed in quotes if it contains spaces and/or special characters.
* Print a variable's value: `echo $<VARIABLE>`, e.g. `echo $PATH`
* Delete a variable: `unset $<VARIABLE>`
* Print all defined variables: `env`


<<<
== Shell Configuration Files
[.step]
* Files with a default configuration are located in `/etc` (without the leading dot); files with user-specific configurations are located in the user's home directory.
* three different (relevant) files:
[.step]
** `.profile` / `.bash_profile` / `.zprofile` for _login_ shells (when logging in to the desktop environment or via SSH / `sudo`): Set environment variables (which are inherited by interactive shells) and run programs once upon login
** `.bashrc` / `.zshrc` for _interactive_ shells (**not** in scripts): Set shell options, define aliases and functions, configure the shell prompt
** `.zshenv` for _all_ shells (Zsh only): Set environment variables that you always want to have


<<<
== Examples of Configuration Files
[source, sh]
----
# .bash_profile
export PATH=~/.local/bin:$PATH  <1>
export LANG=de_DE.UTF-8  <2>

# .bashrc
PS1='\u@\h $ '  <3>
shopt -s extglob  <4>
alias ll='ls -l'  <5>
----
<1> Adding a directory to the search path (`~` is the home directory)
<2> Language settings
<3> Configuring the prompt (`PS1` is not an environment variable because it has not been "exported")
<4> Setting a shell option
<5> Defining an alias

== `sudo`
[.step]
* Tool for running commands as root or as another user: `sudo [-u <user>] <command>`
* Without a command but with the `-i` / `-s` options, you get a login / non-login shell with root privileges or the privileges of the other user.
* is configured via the `/etc/sudoers` file (which users/groups are allowed to use `sudo`, whether a password is required, which commands are allowed to be executed, etc.)
* Two related command:
[.step]
** Display username, UID, and group(s): `id`
** Change password: `passwd`

== Special Files
[.step]
* Links: References to other files/directories; two types of links
[.step]
** Hard links: an additional name for an existing file (both names refer to the same inode); hard links are only possible within a single filesystem and only for files (exceptions are `.` and `..`, as well as macOS); they can only be identified by the number of links
** soft (symbolic) links: a special file that contains the path (absolute or relative) to the target
* Hidden files/directories: begin with a period and are only displayed with `ls -a` (a convention used by shells and programs)
* Device files / devices: used to access hardware such as hard drives (located in the `/dev` directory)
* Pipes and sockets: are a means of communication between processes (not to be confused with sockets used for network communication)


<<<
== Special Directories
[.step]
* interpreted by the operating system (hard links):
[.step]
** current directory: `.`
** parent directory: `..`
* interpreted by the shell (and some programs, such as text editors):
[.step]
** home directory: `~`
** another user's home directory: `~alice`
** previous directory: `-`

== Access Rights (1)
[.step]
* separate access rights (also called _mode_) for the owner (_user_) of a file or directory, the _group_, and _other_ users
* three different rights, represented as a letter or a number (the weight of the corresponding bit):
+
|===
| read | r | 4
| write | w | 2
| execute | x | 1
|===

* In addition, there are also the SUID (4, s), SGID (2, s), and Sticky (1, t) flags; see the slide _Meaning of the Flags_.
* Specifying access rights using letters with `chmod`: 3 groups, each representing the combination of rights and flags for user, group and other, see examples below


<<<
== Access Rights (2)
[.step]
* Output of `ls -l`: 3 groups, each representing the combination of rights for user, group and other; minus signs indicate missing permissions; set flags appear in place of the execute permission, see examples below
* Numeric representation of access rights: 4 digits between 0 and 7 (octal)
[.step]
** 2nd through the 4th digit = sum of permissions for user, group, and other
** 1st digit = sum of the flags
* Unlike in Windows, permissions are not inherited but are defined using a numeric mask (known as the _umask_), which specifies which permissions new files and directories should **not** have (the default value is 0022 or 0002) => The value of the mask is subtracted from 0666 (files) or 0777 (directories).
* In addition to permissions for user, group and other, more granular permissions (for additional users and groups) can be assigned using https://www.redhat.com/en/blog/linux-access-control-lists[_Access Control Lists_] (ACLs) (as in Windows).

== Meaning of the Access Rights
[cols="1,2,2"]
|===
| Permission | File | Directory

| Read (r) | Content can be read. | Content = Names of files/subdirectories can be read.
| Write (w) | Content can be modified. | Files / subdirectories can be created / renamed / deleted, **but only if execute permission has also been granted**.
| Execute (x) | File can be executed (if it is a program or script). | Files and subdirectories can be accessed (metadata and content), and you can navigate to the directory. Files and subdirectories can be created, renamed, or deleted, **but only if write permission has also been granted**.
|===

== Meaning of the Flags
[cols="1,2,2"]
|===
| Flag | Executable file | Directory

| Set User ID (SUID) | Executed with the owner's permissions | -
| Set Group ID (SGID) | Executed with the group's permissions | Newly created files and subdirectories inherit the directory's group (rather than the user's group).
| Sticky | - | Files and subdirectories can only be deleted by the owner (or root) (and not by other users who have write permission on the directory).
|===

[.step]
* All files and directories have three different timestamps:

[cols="1,3,1"]
|===

== Processes (1)
[.step]
* are programs that are executed by the system or are waiting to be executed / for an event to occur
* have (at a given point in time) unique numbers => _Process Identifier_ (PID)
* always have a parent process from which they inherit certain properties and objects (such as open files and environment variables) => tree structure
* The root of the tree is the `systemd` process (or `init` / `launchd`) with PID 1 (which is started by the system at boot time).
* are managed by the _scheduler_ and are assigned in turn to the processor(s) or processor cores.
* are always assigned to a user from whom they inherit their permissions


<<<
== Processes (2)
[.step]
* By default, they have three different input/output channels, which they inherit from the parent process: standard input (_stdin_), standard output (_stdout_), and standard error (_stderr_)
* can consist of multiple _threads_ that can run in parallel on multiple processors or processor cores
* Processes are always in one of the following states:
[.step]
** running \(R) => The process is currently running or is ready to run (is in the queue; the number of processes in the queue is the system load).
** suspended (S) => The process is waiting for an event (e.g. user input, network I/O, or a timer expiring) and can be woken up by signals (see below).
** uninterruptible sleep (D) => The process is waiting for a mass storage I/O operation to complete.
** stopped (T, t) => The process was paused (using Ctrl-Z in the shell or by a debugger).
** _Zombie_ (Z) => The process has terminated, but information is still retained in the kernel (for the parent process).


<<<
== Processes - Memory Management
[.step]
* Each process has its own _virtual memory_ (4 GB on 32-bit systems, 256 TB on 64-bit systems), which contains the program code (of the program and any program libraries it may use) and the data.
* Virtual memory is much larger than physical RAM (on 64-bit systems) => _paging_
[.step]
** Program segments and data are loaded into memory only when needed—that is, the first time they are accessed.
** When memory is scarce, the memory used for program components and data that are not currently in use is reused.
** Data that has been modified but is not currently in use is moved to the _swap_ area of the hard drive(s), and modified data in the _cache_ (a temporary storage area in RAM for mass storage devices) is written to the files.
** If that isn't enough, Linux forcibly terminates individual processes that are using a lot of memory (the so-called https://medium.com/@msmkumar.eee/751cf7823de8[_OOM Killer_]).

== Why text?
[.step]
* Even today, a great deal of data is still stored as text, such as application data (https://en.wikipedia.org/wiki/JSON[JSON], https://en.wikipedia.org/wiki/XML[XML]), program code, configuration (https://en.wikipedia.org/wiki/INI_file[INI files], https://en.wikipedia.org/wiki/YAML[YAML]), documentation (https://en.wikipedia.org/wiki/Markdown[Markdown], https://en.wikipedia.org/wiki/AsciiDoc[AsciiDoc]).
* Text is the universal data format in Linux (files, program input and output).
* Working with text (files) is often easier than working with binary data or databases (and sometimes faster, too).
* Linux/Unix has very powerful tools for working with text; all of these tools can be used with files or in pipelines (using standard input and output).
* Tools allow you to automate tasks and work with large numbers of files (unlike editors).
* There are often three steps in a pipeline: filter, transform, and aggregate

== Regular Expressions
[.step]
* are patterns for searching for and validating strings
* describe the structure of a string without specifying it in full, similar to wildcards in the shell
* Example: An uppercase letter followed by any number of lowercase letters, followed by one or more digits => `^[A-Z][a-z]*\d+$`
* can be used in text editors (find/replace), tools such as `grep`, and all modern programming languages
* various dialects, the most common dialect is _Perl Compatible Regular Expressions_ (PCRE)
* Tutorials: https://developer.mozilla.org/de/docs/Web/JavaScript/Guide/Regular_expressions[Mozilla], https://perldoc.perl.org/perlretut[Perl], https://docs.python.org/3/library/re.html[Python]
* https://developer.mozilla.org/de/docs/Web/JavaScript/Guide/Regular_expressions/Cheatsheet[Cheat Sheet]

== Find and Replace - `sed` / `perl`
[.step]
* often the _transform_ step in a pipeline
* `sed` is suitable for simple cases, namely line-by-line processing and fixed strings.
+
[source, sh]
----
$ sed -e 's/<from>/<to>/g'
----
* The `-i` option performs "in-place" replacement in a file (applies to `sed` and `perl`).
+
[source, sh]
----
$ sed -i -e 's/<from>/<to>/g' <file>
----
* `perl` can search for regular expressions, even across multiple lines.
[.step]
** Search and replace using regular expressions.
+
[source, sh]
----
$ perl -pe 's/<from>/<to>/g'
----
** Search/replace across multiple lines; `-0777` causes the file to be read all at once rather than line by line; with the `s` flag the `.` in the regular expression also matches line breaks.
+
[source, sh]
----
$ perl -0777 -pi -e 's/<from>/<to>/gs' <file>
----

== Extract Strings from Lines - `cut` / `awk` / `perl`
[.step]
* often the _transform_ step in a pipeline
* is equivalent to `SELECT` in SQL
* single column(s) with a fixed delimiter; column index `n` starts at 1; separate multiple columns with commas; the default delimiter is a tab for `cut` and _whitespace_ for `awk` (spaces, tabs)
+
[source, sh]
----
$ cut -d<delimiter> -f<n>
$ awk -F<delimiter> '{print $<n>}'
----
* single column(s), separated by a regular expression; column index `n` starts at 0; separate multiple columns with commas
+
[source, sh]
----
$ perl -F<regular expression> -le 'BEGIN{$, = " "} print $F[<n>]'
----
* regular expression; the parentheses around the expression assign the matched string to the variable `$1`
+
[source, sh]
----
$ perl -nle '/(<regular expression>)/; print $1'
----

== _Optinal_: Filter Lines Based on an extracted string - `perl`
[.step]
* often the _filter_ step in a pipeline
* is equivalent to `WHERE` in SQL
* Output rows in which a specific column matches a regular expression
+
[source, sh]
----
$ perl -F<regular expression> -le 'print if $F[<n>] =~ /<regular expression>/'
----

* Compare a specific column numerically; comparison operators are `==`, `!=`, `<`, `>`, `\<=`, `>=`
+
[source, sh]
----
$ perl -F<regular expression> -le 'print if $F[<n>] == <number>'
----

* Compare a regular expression numerically
+
[source, sh]
----
$ perl -nle '/(<regular expression>)/; print if $1 == <number>'
----

== _Optional_: JSON Structure
[source, json]

[ <1>
    { <2>
        "first_name": "Jane", <3>
        "last_name": "Doe",
        "phone_numbers": [ <4>
            {

== Shell Scripts
[.step]
* are a sequence of commands with arguments and options
* may contain in addition variables and control structures
* may also contain comments; they begin with `#` and continue until the end of the line
* are executed by the shell in exactly the same way as commands entered interactively (with all features such as pipelines, input/output redirection, and background processes)
* They are a full-fledged programming language, but are only suitable to a limited extent for larger programming tasks (better use Python or Perl for those)
* The various shells implement different "dialects" that are not fully compatible => On Linux (and also macOS), you should use Bash for scripts (regardless of which shell you use interactively).

== Variables
[.step]
* can store strings or integers, but are actually type-agnostic (numbers are also stored internally as strings, and strings can be used in arithmetic expressions without causing errors)
* In addition, there are also lists and maps (key-value pairs), but we won't be covering them in this course.
* do not need to be declared

== Using Variables
[source, shell]
----
s=abc  <1>
x=1
nlines=$(wc -l /tmp/blablub.txt)  <2>
echo $abc  <3>

echo "x = $x"  <5>
----
<1> Assignment: If the string contains spaces or special characters, you must use quotes.
<2> _Command substitution_: The output of the command is assigned to the variable.
<3> Access: Prefix the name with a dollar sign.
<4> Arithmetic expression: Variables that contain a string are converted to 0.
<5> _Variable expansion_: The value of the variable is inserted into the string, but only in strings enclosed in double quotes.

== Branches
[source, sh]
----
if [[ $x < 0 ]]; then  <1>
    echo "x is less than 0 ($x)"  <2>

<5> The structure is closed with `fi`.

[source, sh]

== Network - Introduction
[.step]
* Network functionality in Linux is implemented through
[.step]
** Network interfaces = hardware (e.g. network card) + device drivers in the kernel
** Network stack in the kernel that implements protocols such as IP and TCP
** Demons that provide network services such as web servers or SSH
* "Network drives" are typically implemented in Linux using the _Network File System_ (NFS); Windows shares (CIFS) are also supported.


<<<
== Configuring the Network
[.step]
* Network interfaces have one or more IP addresses and the corresponding network _routes_ (gateways) assigned to them.
* Interfaces are usually configured automatically / dynamically (using the DHCP protocol).
* _Name resolution_ (mapping host / computer names to IP addresses) is typically handled by the _Domain Name System_ (DNS); the DNS servers used are also configured via DHCP.
* Alternatively, the network can also be configured manually / statically:
[.step]
** Configuration files for configuring the interfaces; the filename(s) and format depend on the Linux distribution (e.g. Ubuntu / Debian: `/etc/network/interfaces`, RedHat / CentOS / Fedora: `/etc/sysconfig/network-scripts/ifcfg-ethX`) and the software used to manage the network (e.g. https://wiki.archlinux.org/title/NetworkManager[_NetworkManager_] or https://wiki.archlinux.org/title/Systemd-networkd[_systemd-networkd_]).
** Mapping of host / computer names to IP addresses in the `/etc/hosts` file (rarely used these days)
** The `/etc/resolv.conf` file for configuring DNS servers.

| List network interfaces with MAC addresses, IP address(es), and subnet masks +
(Names, e.g. `eth0`, depend on the hardware type and Linux distribution) | `ip addr`

== _Optional_: Access to a remote computer - SSH (1)
[.step]
* _Secure Shell_ (SSH) allows you to work on a computer connected via the network.
* You can log in and work interactively (in the shell) or execute individual commands: `ssh <user>@<hostname or IP address> [<command>]`
* Authentication is performed using a password or a cryptographic key.
[.step]
** You generate a key pair consisting of a public and a private key using the `ssh-keygen` command, which creates the files `id_rsa` (private) and `id_rsa.pub` (public) in the `~/.ssh/` directory.
** You must keep the private key secret (permission 0700 for the directory and 0600 for the file) and you should protect it with a _passphrase_.
** The public key must be added to the `~/.ssh/authorized_keys` file on the **target computer** (this can be done using the `ssh-copy-id` command).
* Computers (hosts) also have a key pair; the public key is automatically added to the local file `~/.ssh/known_hosts` the first time you log in.

== Starting and Stopping a System
[.step]
* At any given time, a Linux system is in a specific state, known as a _run level_ or _target_.
* The `reboot` command boots the system (run level 6), and the `poweroff` command shuts it down (run level 0).


<<<
== Starting and Stopping a System - Run Levels
[cols="1,1,3"]
|===
| Run level | Name | Description

| 0 | Halt | The system is halted / shut down.
| 1 | Single-user mode | The system is running, but only with the necessary services and without networking, for maintenance.
| 3 | Multi-user mode | System is running with all (configured) services and network access, but without a GUI; standard for servers.
| 5 | Graphical mode | Same as 3, plus GUI (desktop environment); standard for workstations
| 6 | Reboot | System is booting.
|===


<<<
== Starting and Stopping a System - `systemd` (1)
[.step]
* When a system boots, a process with PID 1 is started after the kernel starts: `systemd` (`launchd` on macOS). This process
[.step]
** configures the system (devices, network, name resolution)
** starts the services (daemons) that are configured in the `/etc/systemd/system` or `/etc/systemd/user` directory for each run level or target (as symbolic links in a directory named `<target name>.wants/`).
** stops these services again when the corresponding run level or target is exited
** automatically restarts services in the event of an error (process has terminated)


<<<
== Starting and Stopping a System - `systemd` (2)
[.step]
* Each service can be configured in the so-called _unit files_:
[.step]
** Run level / target in which the service should run
** Environment variables
** Scripts / programs to be run before / after startup / shutdown
** Resource limits (CPU, memory, disk space)
* Command for managing services: `systemctl`
[.step]
** View all running services: `systemctl status`
** View / start / stop a specific service: `systemctl status|start|stop <name of the service>`
** Enable / disable a specific service: `systemctl enable|disable --now <name of the service>` (`--now` also starts / stops the service)


<<<
== `systemd` Timers (1)
[.step]
* allow programs / scripts to be run periodically at specific times (by `systemd`), even if the user is not logged in
* are often used to automatically perform maintenance tasks (e.g. backups, deleting temporary files)
* are executed with the respective user's permissions
* replace _cron jobs_ on modern Linux systems


<<<
== `systemd` Timers (2)
[.step]
* two configuration files per program / script:
[.step]
** Configuration of the program / script (which program / script, options, environment variables) => `<name>.service`
+
[source, ini]
----
[Service]
Type=oneshot
ExecStart=/usr/bin/find /tmp -mtime +30 -delete
----
** Configuration of the time(s) at which the program / script should run (in https://man7.org/linux/man-pages/man7/systemd.time.7.html[this] format) => `<name>.timer`
+
[source, ini]
----
[Timer]
OnCalendar=*-*-* 8:00:00 PM

[Install]
WantedBy=timers.target
----

== `systemd` Timers (3)
[.step]
* They can be created system-wide (files under `/usr/lib/systemd/system/`, edit with `systemctl edit --full --force <file>`) or for a specific user (files under `~/.config/systemd/user/`, edit with `systemctl --user edit --full --force <file>`)
* Good tutorials: https://wiki.archlinux.org/title/Systemd/Timers and https://unix.stackexchange.com/a/688512
* Output (standard output / standard error) is collected by the `journald` daemon and can be viewed using `journalctl`.

== Logging (1)
[.step]

| Service | `--unit` (`-u`)

| Priority (from `debug` to `emerg`) | `--priority` (`-p`)

== Storage Media and File Systems
[.step]
* Storage devices (hard drives, disk arrays, CDs/DVDs, USB flash drives) are accessed via device files (in the `/dev` directory).
* Storage devices must use a file system supported by Linux (ext4, FAT32, ISO 9660...).
* _Mounting_ makes the storage device visible as a subdirectory (the _mount point_) in the directory tree; the reverse process is _unmounting_.
* There are several ways to mount a storage device:
[.step]
** by `systemd` during boot; device files and their corresponding mount points must be listed in the `/etc/fstab` file
** automatically (by a daemon) when the storage medium (CDs, DVDs, USB flash drives, removable hard drives) is inserted or connected; these media are usually mounted under `/media` or `/run/media`
** manually using the `mount` command (e.g. `mount /dev/sdb1 /data`); unmount with `umount`
* A device can only be unmounted if no one is currently accessing any files or directories on the device (including as the current directory).

== Package Manager - Introduction
[.step]
* are designed to make it as easy as possible to install (and uninstall) software from a trusted source
* The various Linux distributions use (in some cases) different package managers => Ubuntu / Mint / Debian / Kali: _APT_, Fedora / CentOS / RedHat: _DNF_; see https://www.linode.com/docs/guides/linux-package-management-overview/#comparison-of-package-managers[here] for the complete list.

== Package Managers - Concepts
[.step]
* Software is bundled into a single package (executable programs, libraries, scripts, configuration files) and, if necessary, adapted for the respective distribution (e.g. file paths).
* Dependencies are defined for each package (which additional packages are required), and these may be installed automatically alongside with the package.
* There is a _repository_ (provided by the distribution) containing all available packages (on an installation medium such as a CD, DVD, or USB drive, or on a server). Additional repositories (e.g. from open-source projects or software vendors) can be added.
* Every system has a database containing all installed packages.
* All installed packages can be updated with a single command, which takes dependencies into account (for example, if a particular app does not work with the latest version of a library).

== Package Manager - Important Commands
|===

| Search for a package (in the repository, also wildcards are supported) | `apt\|dnf list <search string>`
| Install a package (with dependencies) | `apt\|dnf install <package>`
| Uninstall a package | `apt\|dnf remove <package>`
| List installed packages | `apt\|dnf list --installed`
| Update all installed packages | `apt\|dnf upgrade`
| Update the list of packages available in the repository (APT only) | `apt update`
|===

== Troubleshooting (1)
[.step]
* Which process is using the most CPU, memory, or (disk or network) I/O bandwidth? `csysdig` (Alternatives: `top`, `htop`, `iotop`, `iftop`, https://github.com/draios/sysdig/wiki/How-to-Install-Sysdig-for-Linux[guide] for installing Sysdig)
* Which process has a specific file or network connection (port) open? `sysdig` or `lsof`
+
[source, sh]
----
$ sysdig -c lsof fd.name=/etc/host
$ lsof /etc/hosts
$ sysdig -c lsof fd.port=53
$ lsof -i :53
----
* Which files or network connections does a specific process have open? `sysdig`, `lsof`, or the `/proc` filesystem (see below)
+
[source, sh]
----
$ sysdig -c lsof proc.name=sshd
$ sysdig -c lsof proc.pid=12345
$ lsof -p 12345
$ ls -l /proc/12345/fd
----

[.step]
* Who is currently logged in? `who`

[source, sh]

== `/proc` file system
[.step]
* is a _virtual_ file system that is created and updated by the kernel during system runtime
* mainly useful for debugging and troubleshooting
* Content, which is provided in individual files, some of which are located in subdirectories:
[.step]
** Information about hardware such as the CPU and memory (`/proc/cpuinfo` and `/proc/meminfo`)
** Information about running processes (one subdirectory per process), such as the command line used to start the process (`/proc/<PID>/cmdline`) and the set environment variables (`/proc/<PID>/environ`)
** Kernel parameters that can be changed while the system is running, such as network settings (`/proc/sys/...`)
* Files can be read using `cat` and modified using `echo ... > /proc/sys/...`.

== Containers
[.step]
* are **virtual** instances of the operating system, all of which run on the same actual system
[.step]
** They all use the same kernel.
** Each has its own file system (which allows for different distributions).
** Each has its own _namespace_ for processes (PIDs), users, and the network => processes and users appear to be "on their own" within a container.
* Resource usage (CPU, memory, disk space) can be limited.
* are typically used with tools such as https://www.docker.com/[_Docker_], https://podman.io/[_Podman_], or https://github.com/containerd/nerdctl[_nerdctl_], as well as https://docs.docker.com/desktop/[_Docker Desktop_] or https://podman-desktop.io/[_Podman Desktop_]
* Tools for managing a large number of containers: https://docs.docker.com/compose/[_Docker Compose_] (better suited for a smaller number on a single machine, e.g. for development) or https://kubernetes.io/[_Kubernetes_] (more suitable for a larger number of containers on clusters of computers)


<<<
== Why Containers?
[.step]
* Applications can be isolated from one another.
* Applications can be delivered "pre-installed," that is, along with the necessary libraries, configuration files, and any required runtime environment (such as the Java Virtual Machine or the Python interpreter).
* Containers are more lightweight than virtual machines and may expose a smaller attack surface (because they contain only the necessary programs and data).
* Containers are also useful for setting up test environments / networks on a single computer (e.g. a developer's workstation).


<<<
== Container Images
[.step]
* represent the container's file system in compressed form (a special type of `tar.gz` archive)
* Some include only the application and its dependencies (_distroless_), but often a Linux distribution is used as the basis (is explained well https://serverfault.com/a/951888[here]).
* You can create them yourself (e.g. using Docker or Podman) and store them locally, or download them from _container registries_ such as https://hub.docker.com/[_Docker Hub_].
* _Dockerfiles_ are the build instructions for images.
* Images cannot be modified => Changes made in a running container are discarded when the container is stopped.

== _Optional_: Run containers (1)
[.step]
* Start a container: `podman run [options] <image>[:<version>] [command]`
* Important options:
+
|===

| `-d` | Start the container in the background (detached)
| `-it` | Start it with standard input and a (pseudo-)terminal for interactive use, e.g. a shell
| `-v <path on the host>:<path in the container>` | Make a file or directory on the host available in the container; paths must be absolute
| `-p <port on the host>:<port in the container>` | Make the container’s open network port(s) available on the host
|===

== _Optional_: Run containers (2)
[.step]
* List running containers: `podman ps`
* Stop a container: `podman kill <ID or name>`
* Start a program (e.g. a shell) in a running container:
[.step]
** The program **is** present in the container image: `podman exec [-it] <ID or name> <program and arguments>`
** The program is **not** present in the container image: `nsenter -t $(podman inspect -f '{{.State.Pid}}' <ID or name>) <namespace> <program and arguments>`
* Access the file system of a running container via the `/proc` file system: `/proc/$(podman inspect -f '{{.State.Pid}}' <ID or name>)/root/`

== Lab: Working with Text - Searching / Filtering (1)
* **Task**: Filter the output of `journalctl` for `systemd` log messages and count these messages.
* **Solution**:
** using `grep`, naive approach. The entire line is searched for the string `systemd`, which can lead to false positives. The `-c` option returns the count.
+
[source, sh]
----
$ sudo journalctl -S today | grep systemd
----

** using `grep` and a regular expression. This ensures that the string `systemd` is found only when it appears as a program name.
+
[source, sh]
----
$ sudo journalctl -S today | grep -P 'systemd\[\d+\]'
----


<<<
== Lab: Working with Text - Searching / Filtering (2)
* **Solution**:
** using Perl. Only the fifth column, which contains the program name, is searched. You have to use a regular expression because `journalctl` appends the PID to the name. Adding `| wc -l` at the end gives you the count.
+
[source, sh]
----
$ sudo journalctl -S today | perl -nale 'print if $F[4] =~ /systemd\[\d+\]/'
----

** using JSON and `jq`. If you omit `| .MESSAGE`, the complete objects—including all attributes—are outputted.
+
[source, sh]
----
$ sudo journalctl -S today -o json | jq 'select(.SYSLOG_IDENTIFIER == "systemd") | .MESSAGE'
----

** using JSON and DuckDB. You can get the count with `select count(*)`.
+
[source, sh]
----
$ sudo journalctl -S today -o json | \
    duckdb -c "select MESSAGE from read_json('/dev/stdin') where SYSLOG_IDENTIFIER = 'systemd';"
----


<<<
== Lab: Working with Text - Aggregation
* **Task**: Group the log messages by program and output the number of messages per program, sorted in descending order.
* **Solution**:
** using `cut`:
+
[source, sh]
----
$ sudo journalctl -S today | cut -d' ' -f5 | sort | uniq -c | sort -rn
----

** Using `cut`, program names without the PIDs:
+
[source, sh]
----
$ sudo journalctl -S today | cut -d' ' -f5 | cut -d'[' -f1 | sort | uniq -c | sort -rn
----

** Using Perl, program names without the PIDs:
+
[source, sh]
----
$ sudo journalctl -S today | perl -nale '$F[4] =~ /([a-zA-Z]+)/; print $1' | sort | uniq -c | sort -rn
----

** Using JSON and DuckDB:
+
[source, sh]
----
$ sudo journalctl -S today -o json | \
    duckdb -c "select SYSLOG_IDENTIFIER, count(*) from read_json('/dev/stdin') group by 1 order by 2 desc;"
----

== Lab: Working in a Network (1)
* **Task**: Ask your partner to find out the IP address of their VM.
* **Solution**:
+
[source, sh]
----
$ ip addr
----

* **Task**: Check whether this IP address is accessible.
* **Solution**:
+
[source, sh]
----
$ ping 192.168.x.x
----

* **Task**: Ask your partner to check whether the TCP port for SSH (22) is open on their VM.
* **Solution**:
+
[source, sh]
----
$ sudo netstat / ss -pan | grep :22  # all ports (-a)
$ sudo netstat / ss -tlpn | grep :22  # filters by the relevant ports: only TCP ports (-t) in the LISTEN state (-l)
----

== Lab: Working in a Network (2)
* **Task**: Log in to your partner's VM using SSH and the username and password ("mvhs" / "mvhs123").
* **Solution**:
+
[source, sh]
----
$ ssh mvhs@192.168.x.x
----

* **Task**: Generate an SSH key pair, copy the public key to your partners's VM, and log in using the SSH key.
* **Solution**:
+
[source, sh]
----
$ ssh-keygen  # Generate a key pair; enter a passphrase
$ ssh-copy-id mvhs@192.168.x.x  # Copy the public key to the target system
$ ssh mvhs@192.168.x.x  # Enter the *passphrase*, not the password
----

* **Task**: Copy a file to your partner's VM.
* **Solution**:
+
[source, sh]
----
$ scp /etc/hosts mvhs@192.168.x.x:/tmp/
----
